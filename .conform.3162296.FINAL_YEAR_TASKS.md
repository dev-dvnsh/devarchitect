## Task 1 — Build packageCategoryMap.json

### What this task achieves

Right now devarchitect stores what technology you declared you would use
in stack.json but has no idea what those technologies actually mean. It
does not know that "express" is a backend framework or that "postgres" is
a database. This file teaches the tool what packages mean at a conceptual
level so it can compare declared intent against reality. This is the
vocabulary that every smart feature in the final year project depends on.

### Prerequisites

Nothing. This is a pure data file, no code needed yet.
Create src/lib/ folder inside your existing src/ folder first.

### What you need to learn

Nothing technical. You need domain knowledge — what packages exist in
Node and Python and what category they belong to. If you are unsure what
a package does, look it up.

### Jot down in notebook

The category names to use — write these down and never deviate from them
because every other task checks against this exact list:

backend-framework, frontend-framework, database, database-driver,
testing, deployment, bundler, css-framework, authentication, orm,
http-client, logging, queue, cache

Why consistent category names matter: if this file says "database" but
your drift command later checks for "db" nothing will ever match. One
source of truth, one spelling, everywhere.

### What to actually do

Create src/lib/packageCategoryMap.json. Think about this structure before
writing a single character. You need to support multiple ecosystems — Node,
Python, Go, Rust at minimum. AND within each ecosystem you need to map
package names to categories. How would you nest that? What key do you use
for the ecosystem — the language name? The package manager name?

Once you have decided the structure, fill it out. For Node you should have
at minimum 5-6 packages per category for the categories that matter most:
backend frameworks, databases, testing, frontend frameworks, ORMs.
For Python do the same. For Go and Rust add at least 3-5 entries total
just to prove the structure generalizes.

Ask yourself: what packages does every Node developer know? What would
someone use for a backend? What databases are most common? What testing
libraries? Fill those in first before worrying about obscure packages.

Also ask yourself: what happens when someone uses a package that is not
in this map? The tool needs to handle that gracefully — not crash, not
pretend it knows. Where would you handle that? Note it down even though
the handling code comes in a later task.

### Easier explanation

You are building a dictionary. The tool will look up a package name in
this dictionary and get back a category. Like looking up "express" and
getting back "backend-framework". The dictionary is organized by ecosystem
first — Node packages under "node", Python packages under "python". Write
it as a JSON file with that nested structure. Fill in real packages you
actually know.

## Task 2 — Build detectStack.js

### What this task achieves

This module looks at any project folder and figures out what technologies
are actually being used — by reading manifest files like package.json and
requirements.txt rather than asking the developer. The output of this
module is what gets compared against what the developer declared in
stack.json. This is the "read reality" half of drift detection.

### Prerequisites

- Task 1 complete — this file imports packageCategoryMap.json
- A test project folder with a package.json that has some dependencies
  so you can actually test the detection

### What you need to learn

1. nodejs fs.readdirSync and fs.existsSync — how to check which files
   exist in a directory without crashing if they are missing.
   Search: nodejs check if file exists in directory

2. How package.json dependencies are structured — open any package.json
   and look at the dependencies and devDependencies fields. They are
   objects where keys are package names and values are version strings.
   How would you extract just the package names?

3. What requirements.txt looks like — each line is either a package name
   or a package name with a version like django==4.2. How would you parse
   that line by line in Node?
   Search: nodejs read file line by line split

### Jot down in notebook

The difference between dependencies and devDependencies in package.json —
dev dependencies are testing tools and build tools. For drift detection
you probably want to check both. Why?

What a detected stack object should look like — it needs the same shape
as stack.json so they can be compared directly later:
  {
    "frontend-framework": ["react"],
    "backend-framework": ["express"],
    "database": ["mongoose"],
    "testing": ["jest"]
  }
Note it is an array per category not a single value because a project
might use multiple things in the same category.

The fallback strategy: what do you do for a project with no recognized
manifest file? You cannot crash. At minimum return an empty object and
note that no manifests were found.

### What to actually do

Create src/lib/detectStack.js. This file exports one function called
detectStack(projectRoot) that takes a path to a project folder and
returns a detected stack object.

Think through the steps before writing any code. How do you know which
ecosystems are present? You check whether certain manifest files exist.
What manifest file means Node is present? What means Python? What means Go?

Once you know the ecosystem, how do you get the package list? For Node you
read package.json and pull out the keys of dependencies and devDependencies.
For Python you read requirements.txt line by line.

Once you have a list of package names, how do you turn them into categories?
You look each one up in packageCategoryMap.json. If it is there you add it
to the detected stack under that category. If it is not there you skip it.

What does the final return value look like? An object with category names
as keys and arrays of detected package names as values. Only categories
where something was actually detected should appear — no empty arrays.

Also think about: what if the project is polyglot — both package.json AND
requirements.txt exist? Should you merge the results or keep them separate
by ecosystem? There is no single right answer but you need to make a
decision and stick with it. Write down why you chose what you chose.

### Easier explanation

You are writing a function that acts like a detective. Give it a folder
path and it looks around for clues — manifest files. Once it finds them
it reads the dependency lists and looks up each package name in the
dictionary you built in Task 1. Whatever it finds it organizes into a
neat object grouped by category. You return that object from the function.

Run it inside your devarchitect project folder:
  node src/lib/detectStack.js

You should see commander, chalk, inquirer, open all detected and

the manifest reading or the category map lookup. Delete the test after.

## Task 3 — Add category inference to decision.js

That category field gets inferred silently from the text the user already
typed — no new question asked. It is what makes the why command searchable
by category and what makes drift detection able to cross-check decisions
against the declared stack. Without this field those features cannot work.

- Task 1 complete — you need packageCategoryMap.json to exist

   package names in one flat list.
   Search: javascript Object.values flatten array

   names — someone might type "mongodb" (a package name) or "database"
   (a category name). You should handle both.

### Jot down in notebook

Why this inference is silent — no new question shown to the user because

## Task 5 — Build compareStack.js

### What this task achieves

This is the brain of drift detection. It takes what the developer declared
in stack.json and what was actually detected in the codebase and produces
a structured diff saying for each category whether things match, mismatch,
or are missing from one side. This module prints nothing and reads no files
— it just does the comparison logic. Separating it from the drift command
means it can be tested independently.

### Prerequisites

- Task 1 complete — packageCategoryMap.json
- Task 2 complete — detectStack.js
- Understand what stack.json looks like — read one from a test project

### What you need to learn

1. How to compare free text against a category — stack.json stores human
   text like "express js" not a normalized package name. You cannot do an
   exact string match against the detected package name "express". You need
   a fuzzy approach: check if any word in the declared text appears in the
   detected package list for that category.
   Search: javascript string includes partial match multiple words

2. Set operations in JavaScript — for finding what is in detected but not
   declared and vice versa.
   Search: javascript array difference two arrays

### Jot down in notebook

The four result types per category:
  match — declared and detected agree
  mismatch — declared says one thing, detected shows something different
  undeclared — detected found something with no matching declaration
  unused-declaration — declared something that was never detected in code

What the output object of this function should look like:
  {
    "backend-framework": {
      "result": "match",
      "declared": "express",
      "detected": ["express"]
    },
    "database": {
      "result": "undeclared",
      "declared": null,
      "detected": ["mongoose"]
    }
  }

The tools field in stack.json is excluded from comparison — it is free text
with multiple values and would produce noisy results. Only compare:
frontend, backend, database, deployment.

### What to actually do

Create src/lib/compareStack.js that exports one function:
compareStack(declared, detected, categoryMap)

declared is the parsed contents of stack.json.
detected is what detectStack() returned.
categoryMap is the parsed packageCategoryMap.json.

Think through each category in turn. For each category that appears in
either declared or detected work out which of the four result types applies.
Start with the simple cases — if detected has entries for a category but
declared has nothing, that is undeclared. If declared mentions something
but detected found nothing, that is unused-declaration. The match and
mismatch cases require actually comparing the text.

### Easier explanation

You are writing a comparison function. It takes "what we said we would use"
and "what the code actually uses" and produces a report of differences per
category. Like a diff tool but for technology choices instead of code lines.
Match means both sides agree. Mismatch means they disagree. Undeclared means

## Task 8 — Build similar-decisions

### What this task achieves

This is the academically interesting command. It uses TF-IDF combined with
cosine similarity to find decisions that are conceptually related even when
they do not share any exact keywords. Two decisions about "reducing latency"
and "choosing a faster ORM" are conceptually linked even though neither
mentions the other's specific words. In your viva this is the command you
point to when asked "what algorithm did you implement?"

### Prerequisites

At least 5-6 decisions recorded in a test project — the algorithm needs
enough documents to be meaningful. With 2-3 decisions everything looks similar.
Understand what TF-IDF is before writing any code — see learn section.

### What you need to learn

1. What TF-IDF is and why it works — do not skip this.
   Search: TF-IDF explained simply
   Search: term frequency inverse document frequency example
   Understand: TF rewards words that appear often in ONE document.
   IDF penalizes words that appear in ALL documents. Together they find
   words that are distinctive to a specific document.

2. What cosine similarity is — after TF-IDF gives you a vector of numbers
   for each decision, cosine similarity tells you how similar two vectors are.
   A score of 1.0 means very similar. A score of 0 means completely unrelated.
   Search: cosine similarity explained simply
   Search: cosine similarity formula

3. How to build a vocabulary from text in JavaScript — collect all unique
   words across all decisions, remove stopwords like "the", "a", "is", "we",
   "use" that carry no meaning, and use that vocabulary as the dimensions of
   your vectors.
   Search: javascript tokenize string into words remove stopwords

### Jot down in notebook — write all of this

TF formula for one word in one document:
  TF = number of times word appears in document / total words in document

IDF formula for one word across all documents:
  IDF = log( total number of documents / number of documents containing the word )
  The log keeps large numbers manageable. More documents containing a word
  means lower IDF — the word is common and not distinctive.

TF-IDF for one word in one document:
  TF-IDF = TF multiplied by IDF
  High score means the word appears often in this document but rarely in
  others — it is distinctive to this document.

Cosine similarity between two vectors A and B:
  similarity = dot product of A and B divided by (magnitude of A times magnitude of B)
  Dot product: multiply matching positions and sum them.
  Magnitude: square each value, sum them, take square root.
  Result is always between 0 and 1.

The algorithm pipeline end to end:

  1. Collect all decision text (what + why + alternatives combined)
  2. Tokenize each into words, lowercase, remove stopwords and punctuation
  3. Build a vocabulary: all unique words across all decisions
  4. For each decision build a TF-IDF vector (one number per vocabulary word)
  5. For every pair of decisions compute cosine similarity
  6. Report pairs whose similarity is above the threshold

Why you need at least 5-6 decisions: IDF needs multiple documents to work.
With 2 documents almost every word is "distinctive" so everything looks similar.

### What to actually do

Create src/lib/similarity.js with these math functions:
  tokenize(text) — lowercase, split on spaces and punctuation, filter
  stopwords and single characters, return array of words
  buildVocabulary(tokenizedDocs) — collect all unique words across all
  documents, return as sorted array
  computeTFIDF(tokenizedDoc, vocabulary, allDocs) — for each word in
  vocabulary compute TF-IDF score for this document, return as array of
  numbers in vocabulary order
  cosineSimilarity(vectorA, vectorB) — implement the formula, return number
  between 0 and 1

Then create src/commands/similar-decisions.js that:
  Reads decisions.json — handle the case where it does not exist
  Combines what + why + alternatives text for each decision into one string
  Calls your similarity functions to build TF-IDF vectors for each decision
  Computes pairwise similarity for every combination of two decisions
  Prints pairs whose similarity is above 0.15
  For each pair prints both decision texts and the similarity score as a percentage

Think about how many pairs there are: with N decisions you have N times (N-1)
divided by 2 pairs. With 10 decisions that is 45 pairs. You only print the
ones above the threshold. What if nothing is above it? Print a message.

The most common mistake here is getting the dot product wrong. Make sure you
multiply matching INDEX positions — vectorA[i] times vectorB[i] — not matching
words by name.

### Easier explanation

You are writing a "find related decisions" command. The algorithm works in
four steps. First, turn every decision's text into a list of words and remove
common words that carry no meaning. Second, build a master list of all unique
words across all decisions. Third, for each decision create a list of numbers
where the number reflects how important that word is to that specific decision.
Fourth, compare these number lists for every pair of decisions. Two decisions
with similar number patterns are about similar topics. Print the pairs that
are most similar.

### Confirm it works

Add at least 6 decisions in a test project including some that should be
conceptually related:
  One about choosing MongoDB for flexibility
  One about avoiding relational schemas
  One about preferring NoSQL over SQL
  One about using Jest for testing
  One about why you chose not to use a testing library
  One about code coverage requirements

Run devarchitect similar-decisions

The first three should appear as similar to each other. The last three should
appear as similar to each other. If MongoDB decisions are matching with testing
decisions something is wrong with the algorithm.

## Task 10 — Build install-hooks

### What this task achieves

Right now drift detection only runs when the developer remembers to type
devarchitect drift. Most of the time they will forget. This command installs
a git pre-commit hook that runs drift automatically before every commit —
warning about drift at exactly the moment new dependencies are being committed.

### Prerequisites

Task 6 complete — the drift command must exist and work.

### What you need to learn

1. What git hooks are and where they live — .git/hooks/ directory inside any
   git repo. A pre-commit hook is a shell script that runs before every commit.
   Search: git hooks pre-commit example

2. How to write a file with execute permissions in Node.
   Search: nodejs write file executable permission fs.chmodSync

3. Why not block the commit outright — blocking commits on drift is too
   aggressive. A warning that lets the commit proceed is friendlier and
   will not make developers uninstall the hook in frustration.

### Jot down in notebook

What the hook script needs to contain — a shell script that calls
devarchitect drift and prints a warning if issues are found. The script
should always exit 0 so it never blocks the commit.

Where to put the hook — .git/hooks/pre-commit in the PROJECT where the
user runs devarchitect install-hooks. Not in the devarchitect repo itself.

What to do if a pre-commit hook already exists — do not silently overwrite
it. The user might have other hooks. Warn them and ask before overwriting.

### What to actually do

Create src/commands/install-hooks.js. It should:
  Check that .git/ exists in the current directory — if not tell the user
  this is not a git repository and exit
  Check if .git/hooks/pre-commit already exists — if yes warn and ask
  whether to overwrite
  Write a shell script to .git/hooks/pre-commit that runs devarchitect drift
  Set the file as executable with fs.chmodSync
  Print a success message explaining what was installed and how to remove it

### Confirm it works

Run devarchitect install-hooks in a test project. Open .git/hooks/pre-commit
and read the script — does it look right? Then install a new package and try
to commit. You should see the drift warning printed before the commit succeeds.
The commit should still succeed — exit 0.
